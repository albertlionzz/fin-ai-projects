# finagent 设计说明

## 一、这个项目要解决什么

把两期（或多期）财务报表放在一起，人工找异常是可行的，但有两个问题：

1. **不可复算**。同一个人隔一周看同一份报表，关注的点可能不一样；换一个人结论又不同。
2. **不可追溯**。结论是"感觉应收增长不太对"，但"不太对"的边界在哪，说不清。

finagent 的做法是把"什么算异常"写成代码：阈值集中在 `RuleBook`，
每条规则有编号、有依据、有严重度。**同一个输入必然得到同一份命中清单。**

这让三件事成为可能：

- 结论可以被质疑——「为什么判定为重大？」→「剪刀差 56.3pct，超过重大线 40pct」
- 规则可以被回测——改了阈值，跑评测集就知道召回率和误报率怎么变
- 流程可以被审计——执行轨迹记录了每条规则的耗时与结果

## 二、三 Agent 的职责边界

| Agent | 输入 | 输出 | 是否用 LLM | 为什么 |
|---|---|---|---|---|
| `ExtractAgent` | 报表文本 / JSON | `FinancialStatement` | 条件使用 | 结构化是确定性任务，正则足够；仅在科目识别不足 8 个时才请模型补充 |
| `AuditAgent` | 两期 `FinancialStatement`（+ 可选 `StatementSeries`） | `Finding[]` | **绝不使用** | 判定必须可复算。这是整个系统的可信度基础 |
| `ReportAgent` | `Finding[]` | 摘要 + 研判 | 优先使用 | 措辞与归因可以容忍波动；输入被限定为已确认发现，模型无法发明异常 |

关键约束：**LLM 的输入只有 findings，没有原始报表。**
即使模型完全失控，它也只能在已确认的事实上胡说，不能凭空创造一条不存在的异常。

`AuditAgent` 的第三个参数 `series` 是后加的，但**没有破坏"绝不使用 LLM"这条边界**——
多期趋势判定同样是纯规则：序列规则 `QUALITY_DRIFT` 与持续性升级都由确定性逻辑完成，
模型连看见序列的机会都没有。

## 三、为什么严重度只有三档

`Level` 用 `IntEnum` 定义了 INFO / WARN / HIGH 三档。

不设更多档位，是因为**档位的意义在于对应动作**：
- 重大 → 需要专项核查（函证、走访、调原始凭证）
- 关注 → 需要解释（向管理层问询）
- 提示 → 记录备查

再加"中高""次高"之类，动作上无法区分，只会增加判断负担。
**分级的粒度应该由可执行动作的数量决定，而不是由感觉上需要多少档决定。**

## 四、风险分的数学选择

线性累加的问题在 README 里详述了，这里补一个更本质的说明：

我们真正需要的性质是「**边际递减但仍单调**」：
- 从 0 项重大到 1 项，风险感知应该有巨大跃升
- 从 9 项到 10 项，跃升应该很小（已经知道问题很严重了）

这正是饱和函数 `1 - e^(-x/k)` 的形状。它在 0 附近斜率最大，
随 x 增大逐渐趋平但永不为 0。

线性累加 + 封顶则完全相反：在接近上限时斜率为 0（信息全丢），
达到上限后完全无区分度。**这是选它做评分函数的唯一理由，不是为了形式好看。**

## 五、评测集的设计

`测试` 里有一组 `EXPECTED_RULES_2025A`，是人工标注的 gold 集合：

```python
EXPECTED_RULES_2025A = {"AR_GAP", "INV_GAP", "OCF_DIVERGE", "DEBT_RATIO",
                        "GOODWILL", "MARGIN_EROSION", "SWING_SCAN"}
```

示例数据里刻意植入了这 7 类异常，测试断言规则引擎必须全部命中。

这和项目一的 `eval_set.json` 是同一个思路：**没有标注集，"我改了规则"就无法量化。**
改完阈值跑一遍，是漏报多了还是误报多了，一眼可见。

另外补了两个反向测试：
- `test_clean_statements_produce_no_findings` —— 健康数据不能报出重大异常（防误报）
- `test_not_triggered_when_receivable_falls` —— 应收下降是好事，不能因为营收也降就误报

**只测"该报的报了"是不够的，还要测"不该报的没报"。** 后者更容易被忽略。

多期趋势这块把反向测试放在了更重的位置，因为新增逻辑的失效模式几乎全是误报：
- `test_flat_series_does_not_fire` —— 四期持平不能算同向恶化（`>= 0` 写成 `> 0` 的原因）
- `test_interrupted_signal_does_not_escalate` —— 中断一期不算持续
- `test_two_periods_skips_trend_entirely` —— 两期输入必须完全退化，不能产出半截趋势结论
- `test_no_escalation_without_series` —— 不传序列时，输出与改造前逐字一致

最后一条是向后兼容的底线：`RuleEngine.run()` 的 `series` 参数默认 `None`，
老调用方（CLI 两期模式、batch 模式、所有既有测试）不需要改一行代码。

## 六、多期趋势：为什么升级原有发现而不是新增一条

需求原话：

> 「连续三年应收增速超营收 20pct」比「今年突然超一次」更值得警惕

这句话拆开是两件事：**判定**（跨期反复命中）和**响应**（更值得警惕该落在哪）。

### 响应落在"升级"，不落在"新增"

直觉做法是命中持续信号时再报一条 Finding。实测有两个后果：

1. **风险分双算**。同一个应收问题，单期一次 + 持续性一次，`risk_score` 里被加两遍。
   饱和函数虽然不触顶，但它会把"一个问题"计成"两个问题"——排序直接失真。
2. **报告里同一问题出现两次**。读者会以为是两个独立问题，核查顺序被打乱，
   而且新增的那条 detail 只能复述一遍已知信息，篇幅上去了信息量为零。

所以实现是**在原 Finding 上做原地升级**：

```python
f.level = _escalate(f.level)                        # WARN → HIGH，HIGH 不越界
f.detail += "该信号在 2023A→2025A 连续 2 个报告期重复出现，非孤立波动，已升级为重大。"
f.basis += "；跨期持续性信号比单期跳变更能说明问题是结构性的"
f.confidence = min(1.0, f.confidence + 0.1)         # 有界递增
```

升级在单轮内是**有界**的：`level` 最高到 HIGH，`detail` 里持续性说明只追加一次
（不是每个命中的配对追加一遍）。测试 `test_escalation_is_idempotent_on_level`
断言 `detail.count("重复出现") == 1` 且 level 不越界。
`_escalate()` 到 HIGH 就停——持续性只能把"关注"提升到"重大"，
不造第四个档位，因为档位的意义在于对应动作（见第三节），动作无法区分就没有必要分档。

### "连续"不是"累计"

判定要求最近 `trend_min_periods - 1` 个**相邻**期配对全部触发：

- 坏、坏、坏 → 持续，升级
- 坏、好、坏 → 中断一期，不升级（这是波动，不是趋势）
- 坏、坏、好、坏 → 只看最近两个配对，前两个不计

中间中断一期不计入，因为**"一次坏、一次好、一次坏"描述的是波动性，
波动性和结构性问题需要完全不同的核查动作**。把两者混为一谈会让"持续"这个词失去信息量。

### 序列规则与两期规则必须分开

`QUALITY_DRIFT` 的输入是整个 `series` 而不是一对 `(cur, prev)`。
如果把它塞进两期规则的签名里，就只能拿到最后一对，看不出趋势。
但两种规则的运行条件不同：序列规则需要 ≥3 期，两期规则永远可跑。

用 `is_series_rule` 标记区分，`RuleEngine.run()` 据此分派：

```python
if rule.is_series_rule:
    if series is None or not series.has_trend(self.book.trend_min_periods):
        continue                      # 序列不足，静默跳过
    f = rule(series, self.book)
else:
    f = rule(cur, prev, self.book)
```

**静默跳过是有意的**：传 2 期数据时，整个系统退化成一个纯两期分析，
行为与加这个功能之前逐字节一致。这是向后兼容，也是测试
`test_two_periods_skips_trend_entirely` 与 `test_series_analysis_is_deterministic`
要守住的东西。

### 单期阈值法的系统性盲区

`QUALITY_DRIFT` 存在的理由是补一个盲区：**每期小幅恶化，每期都够不上观察线。**

长恒电子 fixture 就是照这个设计的——毛利率 29.00% → 27.98% → 26.67% → 25.00%，
每期变动都在 1.3pct 上下，够不上 `GROSS_MARGIN` 的 5pct 关注线。
两期模式下这套数据只能报出 1 项关注（净利率降 1.22pct，够不上 `MARGIN_EROSION` 的 2pct 重大线）。
但四期连起来看，
5 项盈利质量指标全部同向走坏，这是明确的恶化通道。

它的判定不是"所有指标都变坏"，而是**每项指标逐期检查、再数有几项通过**：

```python
deltas = [(vals[i + 1] - vals[i]) * direction for i in range(len(vals) - 1)]
if all(d > 0 for d in deltas):        # 严格大于 0，持平不算恶化
    worsening.append(name)
if len(worsening) < rb.trend_min_agree:
    return None
```

这里踩过一次坑：初版写成 `>= 0`，结果**四期完全相同的数据也触发规则**——
持平被算成"朝恶化方向走"，纯噪声数据报出重大异常。
改成严格 `> 0` 后测试 `test_flat_series_does_not_fire` 钉住。
边界条件写松一格，误报就多一类，这是规则类代码的常态。

## 七、行业基准：阈值该跟谁比

### 问题：全市场统一线必然同时误报和漏报

`AR_GAP` 的 20pct 观察线对软件开发明显太松（该行业应收增速中位数只有 2pct），
对建筑施工又太紧（中位数 18pct，p75 已经 26pct）。
同一条线用在整个市场上，**一部分公司的正常经营会被判成异常，
另一部分公司的真实问题会被放过**。

### 实现：只校准基准线，重大线按比例推导

`_industry_line()` 三条规则：

1. **无基准簿 / 行业不在表里 / 同行样本不足 5 家 → 原样返回绝对线**。
   这是向后兼容底线，也是**不能让参照数据成为单点故障**。
2. **只校准关注线，重大线按 `abs_high / abs_warn` 的原有比例推导**。
   "关注 / 重大"的比例关系是判定策略（需要解释 vs 需要专项核查），
   不该跟着行业样本漂移——否则同一个 30pct 剪刀差在 A 行业是关注、在 B 行业是重大，
   档位的含义就不统一了。
3. **必须返回来源，并写进 `Finding.evidence.line_source`**。
   读者看到"观察线 12pct"时，必须能回答"这个 12 是哪来的"。
   报告正文里另外做一层人类可读翻译（`已按工程机械行业 p75 分位校准`），
   底稿和 JSON 消费方则要精确的 `industry:p75`——两种表示各取所需。

### 校准是双向的

直觉上会把行业校准理解成"提高灵敏度"。实际上它同样在**压制误报**：
`test_calibration_can_suppress_a_finding` 构造了一个建筑施工公司
（该行业剪刀差 p75 = 26pct，比全市场线 20pct 更松），
绝对线下 gap 25pct 会报警，行业线下不报。

只测"校准后能报出更多"会漏掉这半边。**任何一个"相对化"的改动，
都要同时验证它放过了什么。**

### 样本量门槛为什么是 5

3 家同行的分位数不是基准，是噪声。门槛放在 `BenchmarkBook.get()` 一层统一执行，
而不是让每条规则各自判断——"多少家才算够"这条规则只应有一个实现。

fixture 里专门放了一个 `n_peers=3` 的「小众仪器制造」行业，
测试 `test_get_returns_none_below_min_peers` 钉住它必须被忽略。

## 八、参数敏感性：衡量档位翻转，不衡量分数变化

### 为什么不能看分数

分数是连续量。改 `scale` 从 20 到 21，分数必然变——
但档位可能一动不动，建议动作也一动不动。
**拿分数变化当敏感性指标，会得到"处处敏感"的假结论，
进而在伪精确的参数上继续手调。**

真正决定行动的是档位。所以 `scripts/sensitivity.py` 的网格衡量的是
**翻档格数 / 总格数**，输出的是稳健参数区间，不是一张分数波动表。

### ScorePolicy 为什么必须抽出来

参数如果硬编码在 `risk_score()` 方法里，做敏感性就只能另写一份公式。
那份副本会悄悄和主线逻辑漂移，跑出来的"稳健区间"是假的。

所以把 scale、三项权重、三个分数切点、两个严重度门槛
全部收进 `ScorePolicy` 一个 frozen dataclass，`DEFAULT_POLICY` 是线上行为，
任何不传参数的调用方结果不变。敏感性分析走的是**真实的 `risk_grade()`**。

### 一个反直觉的发现

35 个组合里只有 24 个在全部 4 个场景下不翻档（69%）。
但拆开看，三个真实场景稳定性都在 86% 以上，
拉低全局数字的是那个**合成边界探针**（5 项关注、分数 63.21，贴在 65 切点下方 1.79 分）——
它在 scale ≤ 15 时全部翻档。

这个探针是刻意加的：真实场景的档位多由严重度维度决定
（有重大就锁"高"），**测不出分数切点的敏感性**。
不加它，敏感性分析会给出一个虚高的稳定性数字。

### 诚实的边界

无重大异常的场景里，`w_high/w_warn` 比值根本不进入计算
（风险分只由关注项贡献），矩阵整行同值是数学必然。
报告对这类场景单独标注了这句话，**避免把"没测到"读成"很稳健"**。

## 九、审计底稿：证据，不是宣传材料

### 结论区为什么原样保留

`build_working_paper()` 刻意不改写、不润色 analysis 的原始结论：
研判文字与异常明细原样进入底稿。底稿要能被复核人、要被外部检查，
**任何"让结论更好看"的加工都会让它失去证据资格。**

### 程序区是反推的，不是模板套话

勾稽校验执行了 → 记一条"重新计算"程序；
趋势分析执行了 → 记一条"分析程序"并注明趋势区间，索引里多一条 `A-2 多期趋势分析表`；
行业校准生效了 → 记一条程序说明阈值来源。

程序区跟着实际跑过的环节走，所以两期报告的底稿和四期报告的底稿**程序数不同**——
这是应该的，底稿要反映实际做的工作。

### xlsx 为什么允许缺失

Markdown 渲染纯标准库，永远可用。xlsx 依赖 openpyxl，
`render_workpaper_xlsx()` 在缺依赖时**明确报错而不是静默降级**——
静默降级会让使用者以为拿到了表格文件，实际只拿到一半。

CLI 测试里两条路径都验证过（md 永远成功，xlsx 在无 openpyxl 时以非零码退出并说明原因）。

### 一个被测试抓出来的真实缺陷

`Procedure.to_dict()` 输出的键是 `scope`，字段名却是 `scope_`，
`from_dict()` 用 `Procedure(**p)` 还原时直接 `TypeError`——
**序列化出去的东西读不回来**。这类缺陷单看代码极难发现，
因为 to_dict 和 from_dict 各自都是"对的"，
只有 round-trip 测试能让它暴露。`test_to_dict_roundtrip` 钉住了这个约束。

## 十、A/B 框架：先定义"什么叫更好"

### 四个指标，各自防一种失效模式

| 指标 | 防的是什么 |
|---|---|
| 事实保真度 | 模型编造 findings 里不存在的数字 |
| 覆盖率 | 模型只挑顺手的说，漏掉难解释的发现 |
| 复述率 | 模型把 finding 的 detail 换个措辞重抄，没有聚合价值 |
| 可复算度 | 同一输入多次运行结果不一致 |

保真度的判定方式是从 findings **反推"允许出现的数字"集合**，
输出里每个数字都必须能在集合里找到。三个来源缺一不可：
正文数字、evidence 数值、发现计数（"重大 2 项"里的 2）。
漏掉第三类会把所有计数表述判成幻觉，误报率高到指标没法用。

### StubLLM 为什么要有 hostile 模式

`--stub hostile` 会故意往输出里注入一个 prompt 里不存在的数字（87.4%）。
跑一次必须看到它被点名抓出来——**抓不到说明指标是假的。**

框架自检只能证明"管线通、指标有区分度"（模板复述率 0%，stub 75%，对比鲜明），
**不能替代真实模型运行**。所有 `--stub` 输出在报告里都标注了这一点。

3. ~~**参数敏感性分析**~~：已落地。见第八节。35 组合网格、24 个稳健。

   跑法 `python scripts/ab_test.py --api --model qwen-plus`。
